## 3. 过程中的中断与找回（如实记录）

1. **首次尝试 `1536x2048`（A 保守版）被前台 30s 命令上限中断**：请求已到达服务端并成功（`4a7c5068-1c05-4ec1-a202-77676fd63046`），但本地未落盘。为避免与其余五张尺寸不一致，**未采用**该结果，改为统一 `1024x1368` 重跑（现用 `83181b41…`）。该 1536x2048 样本已存在于服务端历史记录中，未下载。
2. **B 保守版被超时中断**（`cb3bb88d…`）：改用 `recover.py` 从服务端历史请求列表中找回并落盘，**没有重新生成、没有额外消耗**。
3. **B 表现版首次发起时连接超时**（`WinError 10060`，请求未到达服务端），重跑成功（`180200b8…`）。
4. **C 保守版首次发起时连接超时**（同上，请求未到达服务端），重跑成功（`94974acb…`）。
5. **一次并发教训**：同时发起"拉取历史列表（响应体约数 MB）"与"生图请求"造成网络拥塞，两者先后失败。此后所有网络操作**严格串行**（一条命令只做一件事）。

机制发现（已写入仓库 `AGENTS.md`）：该 endpoint 支持 `GET .../requests?limit=N` 列出历史请求（含 `request_id` / `status` / `outcome.media_urls`），因此被前台超时"丢掉"的调用**可以找回**，不需要重跑烧额度；仓库新增工具 `recover.py` 固化该能力。

## 5. 记录修正（2026-09-29 复核）

- 复核时用 Pillow 读取实际交付文件，发现 6 张的实际像素是 **1024×1360**；本轮原始记录（6 份 `.provenance.md` 的 `Dimensions` 行、本文档表格）沿用了 API 元数据值 `1024x1368`，属记录错误。
- 原因：该接口把长边向下对齐到 16 的倍数（1368 → 1360），而 `outcome.media_urls[].width/height` 仍回报请求值。
- 处理：6 份 provenance 的 `Dimensions` 行已更正为 `1024x1360` 并加 `Size-Note` 说明；本文档与 `README.md` 同步更正；`recover.py` 已改为下载后用 Pillow 读实际像素。
- 只修正记录，**图片文件本身未做任何改动**。
